1. Headline result: the graph layer does not work

This is the finding, not a footnote.

RingWatch was built to show that a classical graph layer improves fraud detection. Measured honestly on a temporally held-out test set, it does not. Confidence intervals are a paired bootstrap over {{ dataset.test_rows | int }} test rows — both models scored on identical resampled indices, so the comparison is not inflated by test-set variation affecting them equally.

But it reaches almost nothing

Those two numbers side by side are the argument. Fraud genuinely clusters far beyond chance — but {{ ring.all_fraud_components }} rings cannot move a metric averaged over {{ dataset.test_rows }} transactions when the model already has 433 features. Rare structure is real structure, and it still cannot shift an average.

What this does not license: IEEE-CIS has transaction-level fraud labels, not ring labels. RingWatch never claims “N rings caught” — those {{ ring.all_fraud_components }} components are statistically anomalous clusters, not verified rings.

2b. Does it matter where the money is?

The obvious objection to the result above, tested rather than argued.

AUC-PR is count-uniform — it treats a small fraud and a large one identically. PayPal's engineers report optimising for “dollar-weighted fraud detection”, which raises a fair challenge: maybe the graph layer only looks useless because the metric ignores value.

Fraud value in graph-linked rows

{{ "%.2f"|format(vw.concentration.enrichment) }}× enrichment

{{ "%.2f"|format(vw.concentration.count_share * 100) }}% of fraud count vs {{ "%.2f"|format(vw.concentration.value_share * 100) }}% of fraud value. Value weighting can only change a conclusion if the favoured subgroup carries disproportionate value. It does not.

The result that nearly became a false headline

+ centrality — hand-implemented PageRank and Brandes betweenness, the algorithms PayPal names for ring detection — came back significantly better under value weighting (+0.0125, uncorrected 95% CI [+0.0024, +0.0220]) while being significantly worse on counts. That is exactly the dramatic “the graph matters where the money is” story.

It does not survive correction for the eight comparisons actually run — the interval becomes [−0.0022, +0.0257] and spans zero. Reporting the one hit without mentioning the other seven would have been selective reporting. The pre-registration committed in advance to treating any positive as hypothesis-generating, which is what makes this recoverable rather than tempting.

What does survive points the other way: both k-core and centrality are significantly harmful on the count metric.

Why [A] is unshippable despite being “optimal”

No payments team declines {{ "%.2f"|format(ops.cost_minimising.insult_rate * 100) }}% of legitimate traffic. The arithmetic is right; the cost model is incomplete. It prices a missed fraud at full transaction value plus a ₹{{ assumptions.chargeback_fee_inr | inr }} chargeback fee, but prices a false positive at only {{ "%.0f"|format(assumptions.gross_margin_rate * 100) }}% gross margin — because the lifetime-value damage of insulting a good customer is deliberately not monetised, as putting a number on churn would be inventing data. An unpriced cost reads to an optimiser as a free one. Both points are reported; the gap between them is the honest statement of what is missing.

4. Calibration

Are the probabilities trustworthy as probabilities?

AUC-PR is invariant to any monotonic rescaling of the scores, so a model can rank perfectly while its outputs mean nothing as probabilities. That matters here because the operating threshold above is chosen by minimising expected rupee cost — arithmetic that reads each score as a probability.

{{ c.label }} {{ "%.6f"|format(c.brier) }} {{ "%.6f"|format(c.ece) }} {{ "%.6f"|format(c.max_bin_error) }}

How to read the Brier score

It conflates calibration with discrimination/refinement, so it should not be read as a pure calibration metric on its own — a model can improve it purely by separating classes better without becoming better calibrated. ECE is shown alongside because it measures only vertical distance from the diagonal. Both use {{ calibration[0].n_bins }} {{ calibration[0].strategy }} bins, because at a {{ "%.2f"|format(dataset.test_fraud_rate * 100) }}% positive rate equal-width bins would put nearly every row in the first bin.

Why the confidence field is left unvalidated

Each narrative carries a high/medium/low confidence, and RingWatch makes no claim about whether it is accurate. Validating it would need to know which flagged clusters are genuinely rings — and with {{ clusters | length }} clusters and no ring-level ground truth, no such claim is possible. The only ways to manufacture one (grading against transaction labels, or against the engine's own risk score) are circular. That closed loop is exactly why this project's predecessor was abandoned.

6. Live Razorpay webhook

The only part of this page that is not precomputed. {{ event_total }} event{{ '' if event_total == 1 else 's' }} received · JSON feed

Test-mode webhooks are verified by HMAC-SHA256 over the raw request bytes — never a parsed and re-serialised body, which would change the bytes and break the signature on payloads nobody tampered with. Delivery is at-least-once, so x-razorpay-event-id is a primary key and replays are no-ops. The endpoint returns 200 before any analysis runs, because Razorpay disables endpoints slower than about five seconds.

Two tracks, and only one of them is a real assessment

track 1 · real Graph structure. Connected components and k-core over an entity graph built from Razorpay-native identifiers. These are the same implementations validated against networkx in the test suite. Topology makes no distributional assumption, so the algorithms transfer to a new payment ecosystem intact.

track 2 · demonstration The model score. The classifier expects 433 IEEE-CIS features; a Razorpay payload supplies 3. It is shown with a measured coverage figure rather than a vague disclaimer, and it is not an assessment of the transaction — it demonstrates that the ingestion path works.

The contrast is the point: the graph transfers, the trained model does not.
